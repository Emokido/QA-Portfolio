# TF-BUG-008 — 소수 평점을 허용하는 API와 정수 단위 프런트 입력·표시가 불일치함

- 결함 상태: `Open`
- 발견일: 2026-09-01
- 등록일: 2026-09-01
- 기준 프로젝트: 스프린트 1 Java/Spring 완성본과 Next.js 프런트
- 기준 커밋: `e2431223ce2a18c8f944d544cba76b951ce0356d`
- 영향 기능: 리뷰 평점 입력·저장·목록 및 상세 표시
- 테스트 수준: 실제 localhost API·브라우저 UI flow와 정적 코드 상관 분석
- 심각도: `Minor`
- 수정 우선순위: 제품 담당자 결정 필요
- 재현성: API 4.5 생성 1/1 성공, 브라우저 정수 입력 제한 사용자 확인 1/1
- 보고 주체: `Codex with user authorization`, 사용자 Postman·Chrome 직접 실행

> 평점의 허용 단위 자체는 명시된 제품 정책이 없다. 따라서 이 결함은 “반드시 0.5점 단위 입력을 제공해야 한다”는 요구사항 위반이 아니라, API가 소수 평점을 허용·저장하는 상태에서 프런트가 정수만 입력하고 소수 값을 올림된 별 개수처럼 표시하는 계층 간 불일치와 사용자 오인을 근거로 등록한다.

## 1. 요약

인증된 리뷰 생성 API는 `rating: 4.5`를 HTTP 201로 정상 저장한다. 그러나 브라우저 작성 화면은 1~5의 별 버튼만 제공해 정수 평점만 전송할 수 있다. 목록과 상세 화면은 각 별 인덱스에 `i < rating`을 적용하므로 4.5를 5개의 채운 별로 표시한다. 같은 데이터의 입력 가능 범위와 저장 형식, 화면 표현이 일치하지 않는다.

## 2. 추적 연결

`TF-REQ-004 → TF-TC-004 → TF-S7-EXEC-005·007 → TF-S7-OBS-008 → TF-BUG-008`

| 식별자 | 연결 내용 |

| TF-S7-EXEC-005 | Postman에서 `rating: 4.5` 생성 HTTP 201·4/4 Passed |

| TF-S7-OBS-008 | API 소수 허용과 프런트 정수 입력·표시 불일치 |

## 3. 테스트 환경

- 백엔드: Spring Boot 3.2.4, Java 17, `stage7` 인메모리 H2, localhost 8080
- 프런트: Next.js 15.2.4 dev server, localhost 3000
- 인증 저장소: QA 전용 비저장 Redis 6380
- 도구: 사용자 Postman Desktop App, Chrome과 DevTools Network
- 외부 DB·OAuth·메일·실계정·운영 비밀값: 사용하지 않음

## 4. 재현 절차

1. Postman 인증 리뷰 생성 요청에 `rating: 4.5`를 넣고 전송한다.
2. HTTP 201과 생성 성공 응답을 확인한다.
3. 브라우저에서 로그인한 뒤 `/community/write`의 평점 입력을 확인한다.
4. 별을 클릭해 선택 가능한 평점 단위를 확인한다.
5. 커뮤니티 목록 또는 상세에서 API로 생성한 4.5 평점의 별 표시를 확인한다.

## 5. 일관성 오라클

제품은 다음 중 하나의 명시적이고 일관된 정책을 가져야 한다.

- 정수 평점만 지원한다면 API·검증·저장 계층도 소수 입력을 거부하거나 명시적으로 정규화한다.
- 소수 평점을 지원한다면 프런트가 지원 단위로 입력할 수 있고 목록·상세가 저장 값을 정확히 표현한다.

어느 정책을 선택하든 API가 4.5를 저장하면서 프런트가 이를 입력하지 못하고 5점처럼 표시해서는 안 된다.

## 6. 실제 결과

- Postman `rating: 4.5` 리뷰 생성: HTTP 201, Tests 4/4 Passed.
- 브라우저 작성 화면: 1·2·3·4·5 별 버튼만 제공해 소수 평점 선택 불가.
- 목록·상세 화면: `i < rating` 조건으로 별을 채워 4.5가 5개의 채운 별로 표시됨.
- 리뷰 작성과 목록 반영 자체는 성공했으며 TF-S7-EXEC-007은 Pass다.

## 7. 코드 상관관계

- `frontend/src/app/community/review-form.tsx`: `[1, 2, 3, 4, 5]`를 순회하고 `handleRatingChange(star)`를 호출한다.
- `frontend/src/app/community/review-list.tsx`: `i < rating`이면 전체 별을 채운다.
- `frontend/src/app/community/review-detail.tsx`: 목록과 동일한 `i < rating` 조건을 사용한다.
- `backend/src/main/java/com/tripfriend/domain/review/dto/ReviewRequestDto.java`: 평점 필드가 `double`이고 범위만 1~5로 제한한다.

이 상관관계는 실제 API·브라우저 결과를 설명한다. 수정 방향은 제품 평점 정책 결정 후 확정해야 한다.

## 9. 영향과 심각도 근거

- API로 저장된 소수 평점이 화면에서 실제 값보다 높게 보일 수 있다.
- UI 사용자와 API 사용자 사이에 입력 가능한 데이터 정밀도가 다르다.
- 리뷰 생성 자체는 가능하고 핵심 기능 전체를 차단하지 않으므로 `Minor`를 제안한다.
- 평점 집계·정렬·추천이 소수 값을 어떻게 사용하는지는 이번 범위에서 검증하지 않았다.

## 10. 수정 후 재검증 조건

- 제품의 평점 단위 정책을 정수 또는 소수 지원으로 명시한다.
- 작성 UI, API 검증, 저장 형식, 목록·상세 표시가 동일 정책을 사용한다.
- 경계값 1·5와 정책상 최소 증분을 API와 브라우저에서 재검증한다.
- 소수 지원 시 4.5가 5점으로 오표시되지 않는지 확인한다.
- 정수 전용 시 4.5 API 요청의 상태·오류 코드·본문 계약을 확인한다.

## 11. 현재 한계와 금지 주장

- 명시된 0.5점 단위 제품 요구사항은 확인되지 않았다.
- 사용자가 반드시 반별 입력을 제공해야 한다고 확정하지 않는다.
- 브라우저 화면의 노출된 세션 쿠키를 공식 증거로 보존하지 않는다.
- 원본 제품 수정과 수정 후 재검증은 수행하지 않았다.
