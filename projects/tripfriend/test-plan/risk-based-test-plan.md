- 미명시 정책은 `정책 확인 필요` 또는 `현재 동작 관찰`로 남는다.

### 위험 상태 규칙

- 현재 TF-RISK-001~014는 모두 `실행 전 가설(Open hypothesis)`이다.
- 케이스 설계 또는 실행 준비만으로 `Reproduced`나 제품 결함으로 바꾸지 않는다.
- 근거 있는 오라클까지 실행해 불일치가 재현되면 실행 결과를 `Fail`로 기록하고, 재현성과 영향을 검토한 뒤 별도 결함 후보로 등록한다.
- 오라클이 없으면 실제 동작과 사용자 영향만 기록하고 `정책 확인 필요`를 유지한다.
- 환경·테스트 코드·데이터 문제로 검증 지점에 도달하지 못하면 제품 `Fail`이 아니라 `Blocked`로 기록한다.

## 8. 테스트 설계 기법

- 동등 분할: 인증 상태, 작성자 여부, 존재·미존재 ID, 지원·미지원 정렬값을 대표 그룹으로 나눈다.
- 경계값 분석: 제목 2·30자, 내용 10·2000자, 댓글 2·100자, 평점 1·5와 바로 바깥값을 사용한다.
- 결정 테이블: 비로그인·작성자·비작성자 × 생성·수정·삭제 × 리뷰·댓글 결과를 정리한다.
- 상태 전이: 리뷰 생성 → 조회 → 수정 → 삭제와 댓글 생성 → 수정 → 삭제의 저장 상태를 확인한다.
- 조합 테스트: P1에서 장소 필터 × 검색 × 정렬의 대표 조합만 선택한다.
- 오류 추정: null, 누락, 미존재, 음수·0 ID, 미지원 정렬, 비정상 limit를 위험 근거에 따라 선택한다.
- 탐색적 테스트: 정책 미명시 항목은 시간 제한과 관찰 질문을 정하고 현재 동작·사용자 영향·추가 결정 필요를 기록한다.

## 11. 진입·종료·중단 기준

### 5단계 테스트케이스 설계 진입 기준

- 이 계획의 P0/P1/P2와 오라클 구분을 사용자가 검토한다.
- P0 TF-COND-001~011의 범위와 추적 ID가 확정된다.
- 미명시 정책이 임의 기대 결과로 포함되지 않았는지 확인한다.

### 6단계 백엔드 테스트 작성·실행 진입 기준

- 상세 테스트케이스와 데이터가 검토되고 상태가 `Not Run`으로 등록된다.
- Java 17·Gradle Wrapper·H2·Mock 구성과 기준 커밋이 기록된다.
- 실행용 작업본과 비밀 설정 제외 상태를 재확인한다.
- 테스트 코드 작성과 정확한 테스트 명령·횟수에 대한 별도 사용자 승인을 받는다.

### P0 실행 종료 기준

- 승인된 P0 케이스가 검증 지점까지 실행되거나 정당한 `Blocked` 사유가 기록된다.
- 각 실행에 기준 커밋, 환경, 실행자, 기대·실제 결과, 상태와 대표 증거가 연결된다.
- `Fail`은 근거 있는 오라클 불일치로만 판정하고 재현성 확인 전 결함으로 확정하지 않는다.
- 결함 후보는 위험·케이스·실행·증거와 연결되고 후속 재검증 상태를 가진다.
- 미실행 P0가 있으면 이유와 다음 행동을 명시하고 전체 완료로 표현하지 않는다.

### 즉시 중단 기준

- 요구사항에 없는 정책을 기대 결과로 확정해야 한다.
- 비밀값·실제 계정·운영 데이터가 필요하다.
- 원본·감사본 또는 예상 밖 파일 변경이 발생한다.
- 승인 범위를 벗어난 제품 코드 변경, 설치·다운로드, 서버·Docker·DB·네트워크·Git 작업이 필요하다.
- 기준 커밋·작업 경로·Java·Gradle·테스트 프로필이 기록과 다르다.
- 테스트 통과를 위해 assertion 삭제·약화, 오류 무시 또는 제품 코드 우회가 필요하다.
- 환경·테스트 코드 오류로 제품 검증 지점에 도달하지 못한다. 이 경우 원인을 분리하고 `Blocked` 여부를 판단한다.
- P0 완료 전에 대규모 Kotlin·성능·E2E 확대로 범위가 바뀐다.

## 12. 실행 상태와 판정 규칙

| 상태 | 적용 기준 |
|---|---|
| Not Run | 테스트 실행을 시도하지 않음 |
| Blocked | 실행을 시도했지만 환경·도구·테스트 코드·계정·데이터·불명확한 오라클 때문에 제품 검증 지점에 도달하지 못함 |
| Pass | 사전조건을 충족하고 검증 지점까지 실행한 실제 결과가 근거 있는 기대 결과와 일치함 |
| Fail | 검증 지점까지 실행한 실제 결과가 근거 있는 기대 결과와 불일치함 |

- 테스트케이스 정의와 실행 이력을 분리한다.
- 환경 오류·테스트 코드 오류를 제품 `Fail`로 기록하지 않는다.
- 컴파일 성공을 제품 `Pass`로 기록하지 않는다.
- 정책 미명시 항목의 코드와 다른 결과를 자동으로 `Fail`로 기록하지 않는다.
- 현재 신규 `Pass`, `Fail`, `Blocked`는 없으며 모든 제품 테스트는 `Not Run`이다.

## 13. 증거와 추적 전략

### 추적 흐름

`TF-REQ·TF-OBS·TF-NFR → TF-RISK → TF-COND → TF-TC → 실행 ID → 증거 → TF-BUG → 재검증`

- 모든 테스트케이스는 최소 하나의 TF-REQ·TF-OBS·TF-NFR 기준 ID와 TF-COND를 가진다.
- 위험 검증 케이스는 TF-RISK를 추가 연결한다.
- 실행 기록에는 실행 ID, 케이스 ID, 실행 시각, 기준 커밋, 환경, 실행자, 입력·사전조건, 기대·실제 결과, 상태, 증거와 결함 ID를 기록한다.
- 실행 주체를 `User`와 `Codex with user authorization`으로 구분한다.
- 사용자 실행은 공유된 출력·스크린샷을 검토하기 전까지 `사용자 보고`로 구분한다.

### 대표 증거

- P0 정상 CRUD의 대표 요청·응답 또는 테스트 결과
- 작성자·비작성자 권한 결과
- 여행지 변경 전후의 장소 ID 또는 저장 상태
- 최소·최대 경계와 대표 400·403·404 응답
- `Fail`, `Blocked`와 중요 위험의 재현에 필요한 로그·상태

모든 케이스의 중복 스크린샷을 남기지 않는다. 토큰·쿠키·개인정보·로컬 사용자명·절대경로·내부 서버 정보는 가리고, 원본 팀 소스와 비공개 자료를 공개 증거에 복제하지 않는다.

## 14. 결함과 위험 수명주기

### 위험 상태

- `Open hypothesis`: 정적 근거가 있으나 실행 전
- `In Progress`: 검증 케이스 실행 또는 재현 분석 중
- `Reproduced`: 근거 있는 오라클 불일치가 재현됨
- `Closed`: 수정 또는 추가 근거로 위험이 해소되고 재검증됨
- `Accepted risk`: 영향과 근거를 검토한 뒤 미수정 수용을 명시적으로 결정함

### 결함 등록 조건

- 실제 실행이 검증 지점에 도달했다.
- 기대 결과에 요구사항·사용자 확인·명확한 계약 근거가 있다.
- 실제 결과와 기대 결과의 불일치가 재현 가능하다.
- 환경·테스트 코드 문제와 제품 문제를 구분했다.
- 제목, 환경, 사전조건, 재현 절차, 기대·실제 결과, 영향, 증거, 관련 케이스·위험을 기록할 수 있다.

`Fail`은 테스트 실행 결과이고 결함은 검토된 별도 기록이다. 한 번의 `Fail`을 자동으로 결함 확정으로 바꾸지 않는다.

## 15. 학습·사용자 실습 체크포인트

### 4단계 계획 검토

사용자는 다음 내용을 설명하거나 정정할 수 있어야 한다.

1. P0/P1/P2가 결함 심각도나 Pass/Fail이 아니라 실행 우선순위인 이유
2. 테스트 베이시스, 테스트 조건, 테스트케이스와 실행 결과의 차이
3. 요구사항·사용자 확인·코드 계약·현재 동작 관찰 오라클의 차이
4. Service·Controller·Repository·API·UI/E2E 테스트의 역할
5. Not Run·Blocked·Fail·결함과 위험 가설의 차이
6. H2·Mock 최소 환경을 먼저 사용하는 이유와 한계

### 후속 테스트 작성·실행 전

Codex는 사용자가 요청하지 않아도 목적, 대상, 사전조건, 실행 위치, 정확한 명령 또는 IntelliJ 조작, 입력 데이터, Mock·실제 객체, assertion·verify의 목적, 예상 결과, 확인할 화면·로그·파일·상태, 중단 오류, 금지 작업과 공유할 증거를 포함한 실습 안내서를 먼저 제공한다.

사용자 직접 실습은 `Codex 설명 → 승인된 준비 → 사용자 실행 → 결과 공유 → Codex 검토 → 실행 주체·상태 기록` 순서로 진행한다.

## 16. 정책 확인 필요와 현재 동작 관찰 목록

다음 항목은 4단계에서 임의 결정하지 않는다.

1. 리뷰 삭제 시 댓글·조회수의 삭제·유지·차단 규칙
2. 평점의 정수·소수 허용 단위
3. 검색어·장소 필터·정렬의 결합 규칙
4. 페이지네이션 방식과 페이지 크기
5. 리뷰 이미지 업로드 범위
6. 인기 리뷰의 정확한 가중치 공식
7. 동일 리뷰 조회수의 중복 방지 기준
8. Bearer 헤더와 쿠키 인증 중 필수 전달 계약
9. 관리자에게 타인 리뷰·댓글 수정·삭제 권한이 있는지 여부

테스트가 필요한 시점에 `정책 확인 필요` 또는 `현재 동작 관찰`을 기대 결과에 표시한다. 데이터 손실, 권한 우회, 일관되지 않은 서버 오류처럼 정책과 별개로 명백한 사용자 영향이 있으면 그 영향은 별도로 평가한다.
