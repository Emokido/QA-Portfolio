# TF-BUG-015 — 리뷰 수정 화면에 기존 값이 초기화되지 않음

- 결함 상태: `Open — QA execution patch retest passed; product fix pending`
- 발견일: 2026-09-04
- 등록일: 2026-09-04
- QA 실행 사본 재검증일: 2026-09-04
- 발견 경로: Playwright 정상 회귀 `TF-E2E-003-B`
- 기준 프로젝트: 스프린트 1 Java/Spring 완성본과 Next.js 프런트
- 기준 커밋: `e2431223ce2a18c8f944d544cba76b951ce0356d`
- 영향 기능: 인증 사용자의 리뷰 조회·수정·삭제 흐름
- 테스트 수준: Browser UI E2E · API fixture
- 심각도: `Major`
- 수정 우선순위: 제품 담당자 결정 필요
- 재현성: 초기값 전용 baseline 확인 2/2에서 재현
- 보고 주체: `User`, `Codex with user authorization`

> 이 결함은 자동화 테스트를 통과시키기 위해 assertion을 완화한 결과가 아니다. API fixture의 상세 응답이 정상인데도 수정 폼의 제목이 7초 동안 빈 값인 것을 반복 재현했고, 직접 원인 후보였던 Next.js 동적 route 처리를 교정한 뒤에도 동일하게 실패했다. QA 실행 사본에서 리뷰 데이터 로딩 완료 후 폼을 렌더하도록 수정한 뒤 같은 테스트와 전체 정상 회귀가 Pass해 제품 결함으로 등록한다.

## 1. 요약

로그인 사용자가 기존 리뷰의 수정 화면을 열면 상세 API는 원래 제목·내용·평점·여행지 값을 정상 반환하지만 수정 폼의 controlled input이 빈 초기 상태로 남는다. 기존 값이 보존되지 않아 안전한 수정이 불가능하고, 여행지·평점 필수 검증 때문에 정상 수정 PUT에도 도달하지 못할 수 있다.

## 3. 테스트 환경

- Frontend: Next.js 15.2.4 dev server, `localhost:3000`
- Backend: Spring Boot 로컬 H2 실행, `localhost:8080`
- 브라우저 자동화: Playwright Test, 설치된 Chrome channel, worker 1개
- 인증: 환경변수로 주입한 로컬 테스트 회원
- 테스트 데이터: 고유 제목의 API review fixture, `finally` cleanup
- 외부 MySQL·OAuth·메일·배포 환경: 사용하지 않음

## 4. 재현 절차

1. 로컬 테스트 회원으로 로그인한다.
2. API fixture로 고유한 제목·내용, 평점 4, 유효한 여행지를 가진 리뷰를 생성한다.
3. `/community/{reviewId}`에서 해당 리뷰의 상세 내용을 확인한다.
4. `수정` 버튼을 눌러 `/community/edit/{reviewId}`로 이동한다.
5. 제목·내용·여행지·평점의 초기값을 확인한다.
6. 기존 제목을 수정하고 `수정하기`를 눌러 PUT 요청과 결과 화면을 확인한다.

## 5. 기대 결과

- 수정 화면에 API fixture의 기존 제목·내용·여행지·평점이 모두 표시된다.
- 사용자는 변경할 필드만 수정할 수 있다.
- 유효한 수정 제출은 `PUT /api/reviews/{reviewId}` HTTP 200에 도달한다.
- 수정된 상세 내용이 표시되고 삭제·cleanup까지 정상 완료된다.

## 6. 실제 결과

- `GET /api/reviews/{reviewId}`는 원래 제목·내용, `rating=4`, `placeId=1`을 정상 반환했다.
- 수정 URL에는 도달했지만 제목 input의 실제 값은 7초 동안 빈 문자열이었다.
- 초기 실행에서는 여행지·평점 필수 검증에 걸려 수정 PUT이 전송되지 않았다.
- 초기값 전용 assertion을 추가한 사용자 실행과 Codex 재현에서 같은 빈 제목이 확인됐다.

## 7. 실패 분류와 가설 검증

1. 최초에는 테스트 입력이 비동기 초기화보다 빨라 발생한 동기화 문제일 가능성을 두고 `Blocked`로 보류했다.
2. 테스트가 기존 제목·내용·여행지·평점을 먼저 기다리도록 교정했지만 제목은 계속 빈 값이었다. 제품 검증 지점에 도달했으므로 `Fail`로 재분류했다.
3. Next.js가 동적 route `params.id`의 동기 접근 경고를 출력해 첫 원인 후보로 삼았다.
4. QA 실행 사본에서 `params`를 await하도록 수정했지만 동일 Fail이 지속돼 직접 원인이 아님을 확인했다.
5. `ReviewForm`이 상세 데이터를 가져오는 동안 빈 controlled form을 먼저 렌더하지 않도록 로딩 상태를 추가하고 함수형 상태 갱신을 적용하자 동일 테스트가 Pass했다.

이 이력은 실패 원인을 테스트 코드·환경·제품으로 분리하고, 반증된 가설도 삭제하지 않은 디버깅 근거다.

## 8. 코드 상관관계와 추정 원인

- 기준 `ReviewForm`은 빈 `formData`로 즉시 렌더한 뒤 별도 effect에서 상세 리뷰를 비동기로 조회한다.
- 상세 API 응답 자체는 정상이고 locator도 실제 제목 input을 안정적으로 찾았다.
- 동적 route 경고만 교정해도 실패가 유지됐으므로 route params는 단독 직접 원인이 아니다.
- QA 실행 사본에서 상세 리뷰 로딩이 끝날 때까지 폼 렌더를 보류하고 `setFormData(current => …)`를 사용하자 빈 초기값 현상이 사라졌다.

따라서 직접 관찰 가능한 원인은 `수정 폼의 비동기 초기값 반영 실패`다. 내부 원인은 초기 렌더와 비동기 상태 반영의 lifecycle 경쟁으로 추정하지만, 이번 범위에서 React 내부 원인을 단독으로 확정하지 않는다.

## 9. 영향과 심각도 근거

- 사용자가 기존 리뷰 값을 확인하거나 일부 필드만 안전하게 수정할 수 없다.
- 필수 여행지·평점이 비어 정상 수정 요청 자체가 차단될 수 있다.
- 리뷰 CRUD의 핵심 수정 흐름을 직접 훼손하므로 `Major`를 제안한다.
- 리뷰 조회·신규 작성·댓글 등록의 전체 실패는 확인되지 않았다.

## 10. 승인된 QA 실행 수정

원본 팀 저장소가 아닌 `QA-Lab/execution/TripFriend`에만 다음을 반영했다.

- 수정 route의 `params`를 비동기로 해석해 Next.js 경고 제거
- `ReviewForm`에 상세 리뷰 로딩 상태 추가
- 데이터 로딩 완료 후 폼 렌더
- 기존 상태를 보존하는 함수형 `setFormData` 사용

route params 교정만으로는 실패가 유지됐고, 폼 로딩 제어까지 적용한 뒤 Pass했다. 이 수정은 원인 분리와 후속 검증을 위한 QA execution patch이며 원본 제품 수정 완료를 뜻하지 않는다.
